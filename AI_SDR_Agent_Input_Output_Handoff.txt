AI SDR Agent Input & Output Handoff
Integration contract for ICP, Account Discovery, Contact Discovery, and Enrichment
Purpose: Use this document to align agent owners on the exact fields each agent must receive and produce. The formal integration contracts for Account Discovery, Contact Discovery, and Enrichment appear in Sections 3–5.

1. End-to-End Handoff
The agents form one pipeline. Every record must retain stable IDs so results can be joined and audited.
ICP Agent   → Account Discovery Agent       → Contact Discovery Agent           → Enrichment Agent               → Intent / Lead Scoring / Personalization

ICP defines what a good target looks like.
Account Discovery finds companies matching that definition.
Contact Discovery finds relevant decision makers inside each selected account.
Enrichment researches those accounts and contacts, producing cited sales intelligence.

5. Exact Enrichment Agent Input
The Enrichment Agent combines the ICP context, one Account Discovery record, and zero or more Contact Discovery records. Only company_name is technically mandatory, but the complete contract below materially improves accuracy.
{   "account": {     "account_id": "acc_123",     "company_name": "Johnson Fitness",     "website": "https://www.johnsonfitness.com",     "linkedin_url": "https://linkedin.com/company/johnson-fitness",     "industry": "Fitness Equipment",     "location": "United States",     "employee_count": 500,     "revenue_range": "mid-market",     "source": "account_discovery",     "fit_score": 87   },   "contacts": [     {       "contact_id": "con_456",       "account_id": "acc_123",       "full_name": "Sarah Miller",       "title": "VP Sales",       "department": "Sales",       "seniority": "VP",       "email": "sarah@example.com",       "linkedin_url": "https://linkedin.com/in/sarah-miller",       "source": "contact_discovery",       "confidence": 0.82     }   ],   "icp_context": {     "icp_id": "icp_001",     "version": 1,     "target_personas": ["VP Sales", "Director of Revenue Operations"],     "pain_points": ["slow lead follow-up", "quote conversion gaps"],     "offer_summary": "AI SDR platform",     "exclusions": {"customer_statuses": ["existing_customer"]}   },   "collection": "sdr_enrichment",   "search_provider": "searxng",   "top_k": 8,   "auto_fetch_and_index": true,   "llm_provider": "ollama_local",   "llm_model": "llama3.2:3b" }

Enrichment Output
Company summary, products/services, target customers and contact briefs.
Recent business signals with confidence and supporting source URLs.
Pain-point hypotheses clearly distinguished from verified facts.
Personalization angles and recommended next action.
Citations, OpenSearch collection, confidence score, timestamps and audit metadata.
6. Account Discovery Interface Requirements
account_id must remain stable across reruns and data sources.
Website/domain should be verified when available; unverified values must be explicitly flagged.
Duplicate companies across CRM, web, enrichment providers, and event lists must be resolved to one canonical account.
fit_score must use a documented scale, preferably 0–1 or 0–100 consistently.
fit_reasons should accompany the numeric fit score for explainability.
ICP exclusion rules must be applied before accounts are returned or recorded as explicit warnings.
Industry, geography, revenue, and employee-count values must use documented normalization rules.
Source and discovery timestamp fields must be retained for auditability.
Output must conform to the JSON contract in Section 3.
7. Contact Discovery Interface Requirements
Every contact must contain the exact account_id produced by Account Discovery.
Duplicate people across sources must be resolved to one canonical contact.
Title, department, and seniority should be normalized to a shared taxonomy.
persona_match_score and identity confidence should be represented as separate values.
LinkedIn URL or another public profile URL should be included when available.
Email and phone verification status should be represented separately from the raw values.
Source, consent, and applicable licensing metadata must be preserved.
Former employees and stale contacts should be detected or explicitly flagged.
Output must conform to the JSON contract in Section 4.
8. Integration Acceptance Checklist
☐ account_id is stable, unique, and reused by Contact Discovery.
☐ contact_id is stable and unique.
☐ company_name and full_name are never empty.
☐ Website/domain and LinkedIn URLs are validated when present.
☐ Scores document their scale and meaning.
☐ Sources and timestamps are retained.
☐ ICP exclusions are applied or explicitly flagged.
☐ Unknown values are null, not invented placeholder text.
☐ Payloads validate against the shared Pydantic schemas.
☐ A sample batch is tested end-to-end before live provider integration.
Mandatory join rule: Account Discovery and Contact Discovery outputs must conform to the JSON contracts in Sections 3 and 4. Every contact must carry the same account_id as its parent account.
